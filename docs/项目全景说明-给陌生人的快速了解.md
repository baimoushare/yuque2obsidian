## 1. 一句话说明这个软件

这是一个**把语雀内容迁移到本地 Markdown / Obsidian 的桌面导出工具**。

它不是单纯“把文章下载成 `.md`”的脚本，而是一个已经明显朝“**语雀 -> 本地知识库 -> Obsidian 可长期使用**”方向演进的桌面软件雏形：

- 有桌面界面
- 能登录、扫描知识库、树形选择导出范围
- 会下载图片、附件和复杂内容
- 会重写内部链接与资源路径
- 会生成失败日志、状态文件、报告文件
- 已经开始对画板、数据表、电子表格、加密块做结构化处理

如果只用一句更准确的话概括它：

**它是一个以“稳定迁移”和“Obsidian 可落地”为目标的语雀桌面导出器。**

## 2. 这个项目真正要解决的问题

从文档、代码和提交记录综合来看，这个项目要解决的不是“导出一篇 Markdown”这么简单，而是下面这组实际迁移问题：

### 2.1 语雀内容不只是普通 Markdown

真实语雀内容里常常混有：

- 图片
- 附件
- 内部文档跳转
- 表格
- 数据表
- 电子表格
- 思维导图 / 画板
- 加密文本块
- 页面型嵌入卡片

这意味着“只拉正文 Markdown”并不能完成真正的迁移。

### 2.2 用户真正想要的是“迁到本地后还能继续用”

这个项目明显把目标定在：

- 本地长期保存
- 迁移后资源不断链
- 笔记之间还能继续跳转
- 最好能直接放进 Obsidian Vault 中使用

所以它特别重视：

- 相对路径
- 统一资源目录
- Obsidian 兼容链接
- 导出后目录结构可维护

### 2.3 迁移任务通常很大，失败不能重来一遍

大型知识库导出时，最怕的是：

- 导到一半失败
- 某几篇失败拖垮整批任务
- 失败后不知道哪篇出了问题
- 第二次只能全量重跑

这个项目为此专门做了：

- 失败 CSV
- 导出状态文件
- 暂停 / 恢复
- 增量导出
- 按失败日志重导

所以它解决的是一个非常现实的迁移工程问题：

**如何把语雀知识库尽可能完整、稳定、可追踪地迁到本地 Obsidian 生态里。**

## 3. 最适合谁使用

这个软件最适合下面几类人：

- 想把个人语雀知识库迁到本地的人
- 想把语雀内容导入 Obsidian 的人
- 有多个知识库、需要批量迁移的人
- 对“资源别丢、链接别断、失败可追踪”有要求的人
- 更偏向 Windows 本机使用、愿意通过桌面程序操作的人

不太适合的场景也要说清楚：

- 追求完全无损恢复语雀全部复杂交互的人
- 期望跨平台成熟安装包、开箱即用发行版的人
- 只需要一段极简 CLI 脚本的人

它当前更像：

**一个已经很实用的个人 / 小团队迁移工具，而不是完全产品化的通用商业软件。**

## 4. 你可以把它理解成怎样的一套系统

当前项目采用的是非常清晰的三层结构：

### 4.1 桌面壳

由 Python `pywebview` 驱动，负责：

- 启动桌面窗口
- 管理本地配置
- 弹出目录选择器
- 启动 Node.js 子进程
- 收集导出日志、进度和结果
- 处理暂停、取消、状态轮询、崩溃报告

核心入口：

- `desktop_app.py`

### 4.2 前端界面

由本地静态页面组成，负责：

- 显示配置项
- 显示登录状态
- 扫描并渲染知识库树
- 支持勾选知识库 / 文档
- 展示整体进度、当前知识库进度和实时日志
- 提供失败 CSV 重导入口

核心文件：

- `desktop/ui/index.html`
- `desktop/ui/styles.css`
- `desktop/ui/app.js`

### 4.3 导出内核

由 Node.js 实现，负责真正的导出业务：

- 读取 Cookie 并验证登录态
- 扫描语雀知识库与目录树
- 拉取 Markdown 与文档详情
- 下载图片 / 附件
- 识别普通文档、画板、数据表、电子表格等不同路线
- 处理复杂块、失败降级、报告输出
- 落地 Obsidian 兼容目录与辅助文件

核心目录：

- `src/`

这三层关系可以理解为：

**Python 桌面层负责“把工具做成软件”，Node 导出内核负责“把语雀内容真正迁下来”。**

## 5. 当前已经具备的核心能力

结合 README、文档、代码和测试，当前仓库已经具备的能力可以概括为以下 10 类。

### 5.1 登录与会话复用

- 使用 `cookies.json` 复用语雀登录态
- 支持手动登录流程
- 可识别当前登录账号
- 启动后可自动判断是否已登录

### 5.2 知识库扫描与树形选择

- 扫描当前账号可访问的知识库
- 获取知识库目录树
- 支持折叠 / 展开
- 支持整库选择
- 支持文档级选择
- 支持 `Ctrl` / `Shift` 多选交互

### 5.3 Markdown 导出

- 获取语雀文档 Markdown
- 清洗语雀 Markdown 中的异常结构
- 转换部分语雀提示块为 Obsidian Callout
- 输出本地 `.md` 文件

### 5.4 图片、附件与媒体资源处理

- 下载图片
- 下载附件
- 把远程链接改写为本地相对路径
- 对部分音视频附件做内嵌处理
- 对下载失败图片写入占位说明而不是直接丢失上下文

### 5.5 内部链接与 Obsidian 兼容

- 识别语雀内部文档链接
- 重写为本地 Markdown / Obsidian 风格链接
- 统一资源目录布局
- 可直接输出到普通 `output/`
- 也可直写到 Obsidian Vault 或 Vault 子目录

### 5.6 复杂内容处理

项目已经不再把所有文档都当成“普通 Markdown 页面”处理，而是开始分路线：

- 普通文档
- 画板 / 思维导图 / 流程图
- 数据表
- 电子表格
- 加密文本块

对应策略包括：

- 尽量结构化导出
- 不适合结构化时保留截图或降级产物
- 避免因为复杂块失败而让整篇文档完全报废

### 5.7 数据表与电子表格落地

从 `table.js`、`sheet.js`、`obsidian.js`、`exporter.js` 以及测试可以确认，项目已经支持：

- 识别语雀数据表文档
- 拉取数据表记录
- 标准化字段和值
- 生成 CSV / JSON / HTML 等 sidecar 文件
- 写入适配 Obsidian Bases 的 dataset 文件
- 识别语雀电子表格并导出工作簿 / 工作表辅助文件

这已经说明项目的目标不只是“保住一份截图”，而是在努力保留结构化数据价值。

### 5.8 加密块处理与重加密

- 支持配置多组密码
- 导出时逐个尝试解锁加密块
- 可记录密码不匹配问题
- 可按策略重加密为 Meld 兼容密文

这是一个很有辨识度的功能，说明项目在处理“迁移后继续可用”而不是仅仅“导出看看”。

### 5.9 稳定性、容错与恢复

- 单篇失败不中断整批任务
- 失败立即写入 CSV
- 输出状态文件 `.yuque-export-state.json`
- 增量导出
- 暂停 / 恢复
- 按失败 CSV 自动生成重导计划
- 复杂块 worker 崩溃后可重试 / 降级
- 资源断链后尝试修复

### 5.10 桌面发布与打包

- 提供 `build_windows_exe.ps1`
- 提供 `YuqueExporterObsidian.spec`
- 使用 PyInstaller 进行 Windows 单文件打包
- 打包阶段增加 EXE 校验
- 失败时保留临时目录用于诊断

这意味着项目已经不是“只有源码自跑”，而是明确在向可分发桌面程序推进。

## 6. 软件内部是怎么工作的

站在执行链路上，这个软件大致按下面顺序工作：

1. 用户启动桌面程序
2. `desktop_app.py` 加载内嵌前端页面并暴露 Python API
3. 前端读取 `desktop.settings.json`
4. 桌面端检查 `cookies.json` 是否可用
5. 如果有登录态，则扫描知识库并生成树形数据
6. 用户选择导出范围、输出目录、Obsidian 相关设置等
7. 前端把配置交给桌面层
8. 桌面层启动 Node CLI 子进程
9. `src/cli.js` 解析配置并分发到 `scan` / `export` / `login` 等命令
10. `src/exporter.js` 构建导出计划并逐篇处理文档
11. 导出中持续输出进度事件、日志事件和结果事件
12. 桌面层轮询任务状态并同步到 UI
13. 导出完成后输出 Markdown、资源目录、失败 CSV、报告文件、状态文件等

这个流程有两个关键特点：

- UI 和导出逻辑分离得比较清楚
- 导出过程是“事件驱动 + 状态可落盘”的

所以它比一次性脚本更适合长任务和失败恢复。

## 7. 导出结果最终会长成什么样

当前输出结果通常不仅仅有 `.md` 文件，还会包含一整套辅助产物。

### 7.1 Markdown 正文

- 每篇导出成功的文档会落成 `.md`
- 尽量保留原始目录层级

### 7.2 知识库级资源目录

典型布局包括：

- `_assets/images`
- `_assets/files`
- `_assets/blocks`

作用分别是：

- 图片
- 附件
- 复杂块截图或补充资源

### 7.3 报告与状态文件

当前代码和文档都表明会生成：

- `export-report.json`
- `export-manifest-*.json`
- `export-failures-*.csv`
- `export-failures-latest.csv`
- `.yuque-export-state.json`

这些文件分别用于：

- 汇总本次导出情况
- 记录导出清单
- 记录失败文档
- 提供最近一次失败日志
- 支持增量 / 恢复 / 跳过已导出内容

### 7.4 结构化 sidecar 文件

针对数据表、电子表格、画板等内容，代码中已经支持额外生成：

- `.csv`
- `.json`
- `.html`
- `workbook.*`
- Obsidian dataset 相关文件

这部分非常重要，因为它说明项目已经在尝试“正文 Markdown + 补充结构化文件”的组合落地。

## 9. 这个项目最有辨识度的设计选择

把所有资料合起来看，这个项目有几条非常鲜明的设计取向。

### 9.1 不是追求“纯净”，而是追求“迁得下来”

复杂内容处理上，它明显接受：

- 正文优先
- 结构化优先
- 实在不行就截图 / 降级 / 占位
- 但不要整批任务因此全废

这是一种很务实的迁移工具思路。

### 9.2 不把失败藏起来，而是把失败变成可管理对象

失败 CSV、状态文件、告警区块、崩溃报告、重导计划，这些都说明作者并没有把失败当异常边缘情况，而是当成迁移过程的常态来设计。

### 9.3 明显偏向 Obsidian 落地

从这些特征可以确认 Obsidian 是第一目标生态之一：

- 相对路径
- WikiLink 风格内部链接
- `_assets` 资源布局
- Vault 直写
- Bases 支持
- `base-board` 插件辅助

### 9.4 桌面端是为了降低使用门槛，而不是炫技

桌面壳的价值主要在：

- 让登录、扫描、选择、导出更可视化
- 让长任务进度可观察
- 让失败恢复和重导更顺手

所以桌面层更多是“降低复杂迁移流程的操作成本”。

- 加密块重加密
- 复杂块 worker 重试与降级
- 资源断链修复
- 渲染截图回退
- Obsidian 兼容路径与配置

这说明项目最被重视、也最容易出问题的部分，就是 Node 导出内核。

### 11.2 测试体现出作者对“边缘失败场景”的重视

从测试名称就能看出来，作者特别关注：

- 白图 / 空截图防误判
- 图片断链后的修复
- worker 崩溃后的重试
- 编辑模式截图时的误匹配
- 加密块密码不匹配
- 复杂块导出失败后的降级行为

这和项目整体“迁移稳定性优先”的思路是一致的。

### 11.3 相对薄弱的地方

从当前仓库看，以下部分测试相对少一些：

- 桌面前端 UI 行为的自动化测试
- `pywebview` 桌面壳端到端测试
- 打包后的发行版验证

所以可以理解为：

**这个项目的可靠性主要建立在 Node 导出内核测试上，桌面 UI 更偏人工验证。**

## 12. 当前已知边界与限制

一个陌生人要快速了解项目，也必须知道它还没有解决什么。

### 12.1 复杂内容不保证完全无损可编辑

尤其是：

- 画板
- 思维导图
- 数据表的复杂视图
- 语雀特有卡片

当前策略更多是：

- 能结构化就结构化
- 否则尽量保真
- 再不行就降级留痕

### 12.2 导出依赖浏览器环境与登录态

项目依赖：

- `cookies.json`
- Puppeteer
- 本机浏览器或打包内置浏览器运行环境

所以它不是一个完全脱离语雀前端生态的纯 API 导出器。

### 12.3 当前平台重心明显在 Windows

这从这些事实都能看出来：

- PowerShell 打包脚本
- PyInstaller 配置
- Windows 路径处理
- Windows 浏览器候选路径
- WebView2 相关发布目录

### 12.4 还处在“强可用、未完全产品化”的阶段

它已经很好用，但仍保留明显的工程型特征：

- 根目录仍存在本地配置文件约定
- 发布流程偏手工
- 发行版说明和最终版本治理仍可继续完善

## 14. 对这个项目当前阶段的总体判断

如果站在“陌生人快速理解”的角度，当前最准确的评价不是“一个导出脚本”，而是：

**一个已经具备较强迁移实战能力的 Windows 桌面导出工具，核心目标是把语雀知识库稳定迁移为适合本地保存与 Obsidian 使用的 Markdown 资料，并通过失败日志、增量状态、复杂块降级和结构化 sidecar 文件，尽量降低大规模迁移的风险。**

它当前最成熟的部分是：

- 导出内核
- 路径与资源处理
- 失败记录与恢复能力
- Obsidian 兼容落地

它最值得继续打磨的部分是：

- 发行版交付体验
- 桌面 UI 自动化验证
- 复杂块的进一步结构化与保真

## 15. 最后给陌生人的一个超短结论

如果你只记住三件事，请记住这三点：

1. 这不是“语雀导出 Markdown 的小脚本”，而是一套面向 Obsidian 迁移的桌面工具。
2. 它最核心的价值不是导出成功一次，而是复杂内容尽量保住、失败可追踪、任务可恢复。
