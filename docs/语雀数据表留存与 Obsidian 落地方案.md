# 语雀数据表留存与 Obsidian 落地方案

## 1. 背景结论

语雀中的“数据表”并不适合直接无损映射成 Obsidian 原生的“Excel 式可编辑表格”。

原因在于：

- 语雀数据表本质上属于富交互复杂块，而不是普通 Markdown 表格
- Obsidian 原生可稳定消费的格式主要是：
  - Markdown 表格
  - CSV 导入
  - HTML 导入
  - 基于属性与文件集合构建的 Bases 视图
- 因此，语雀数据表无法依赖单一格式做到“样式、结构、交互”三者完全保真

本项目最终采用的方向是：

> 结构化数据优先保留，同时保留 HTML 与 PNG 作为兜底。

也就是：

- 优先导出可复用的通用格式
- 同时保留原貌可回看材料
- 确保数据可长期迁移、可再次加工、可在 Obsidian 中继续利用

---

## 2. 总体策略

对于语雀数据表，采用“结构化优先，视觉兜底”的双轨导出策略。

### 2.1 主格式

每个检测到的数据表，固定导出以下 sidecar 文件：

- `table.csv`
- `table.rows.json`
- `table.schema.json`
- `table.html`
- `table.png`

### 2.2 设计目标

- `CSV` 面向 Excel、Google Sheets、Obsidian CSV Importer 等通用工具
- `rows.json` 用于保留更完整的行数据和 richer cell payload
- `schema.json` 用于保留列定义、列顺序、类型、可选值等结构信息
- `HTML` 用于接近原貌浏览或后续 HTML 导入
- `PNG` 作为最终视觉兜底，确保最差情况下仍可查看内容

### 2.3 不追求的目标

当前方案明确不追求以下能力：

- 不输出 `.xlsx` 作为主格式
- 不承诺将语雀数据表 1:1 复刻为 Obsidian 原生数据库
- 不依赖单一未验证的私有接口作为唯一结构化来源

---

## 3. Markdown 落地方式

语雀数据表导出后，会在 Markdown 中统一插入“语雀数据表导出”区块。

区块内容包括：

- 数据表标题
- CSV 链接
- 完整行 JSON 链接
- 表结构 JSON 链接
- HTML 视图链接
- PNG 快照链接
- 一个简短的 Markdown 预览表

预览表只展示前几行，用于：

- 保持正文可读
- 避免大型数据表导致 Markdown 失控
- 让用户在 Obsidian 中快速判断数据表内容

如果页面中的卡片占位与数据表数量可以稳定匹配，则优先将该区块插回到原文占位位置；否则在文末统一追加“语雀数据表导出”章节。

---

## 4. 导出结果目录结构

当前实现兼容现有知识库级 `_assets` 结构，不为每篇文档单独重构整个资源目录。

数据表 sidecar 固定落到：

```text
_assets/datatables/<文档标识>/<数据表名称>/
```

目录内固定文件为：

```text
table.csv
table.rows.json
table.schema.json
table.html
table.png
```

这样做的原因是：

- 不破坏当前图片、附件、复杂块快照的既有目录布局
- 便于按文档定位相关数据表
- 便于长期备份、同步和手工排查

---

## 5. 数据提取分层策略

### 5.1 第一层：页面可见结构提取

优先从页面中已经渲染出来的可见结构提取数据，包括：

- 普通 `table` DOM
- `aria-grid`
- 行列头结构
- 可读文本单元格

这是最稳定、最不依赖内部实现细节的一层。

### 5.2 第二层：结构化前端状态补充

如果数据表容器内存在可读的结构化前端状态，例如：

- `application/json`
- 数据列定义
- 容器属性中的元信息

则一并保留到 `schema.json` / `rows.json` 中，作为 richer metadata。

### 5.3 第三层：视觉兜底

如果结构提取不完整，或只能拿到局部结构：

- 仍导出 `CSV`
- 仍导出 `JSON`
- 仍保留 `HTML`
- 同时强制保留 `PNG`

并将该数据表标记为：

- `partial: true`

用于提醒后续人工复核。

---

## 6. 值归一化规则

为了让 CSV 更适合作为通用交换格式，当前值归一化规则如下：

### 6.1 直接写入 CSV 的类型

以下内容优先写成单元格可读值：

- 纯文本
- 数字
- 日期
- 布尔值
- URL

### 6.2 降级写入 CSV 的类型

以下内容在 CSV 中转成便于阅读的文本：

- 多选值：使用分号拼接
- 标签：使用分号拼接
- 链接对象：优先写 URL 或显示文本
- 附件对象：优先写名称或 URL
- 成员对象：优先写名称
- 引用记录：优先写名称或标识文本

### 6.3 不追求 CSV 无损表达的类型

以下内容不强求在 CSV 中无损表达：

- 富文本
- 公式
- 嵌套块
- 关联字段
- 复杂对象数组

这些内容统一策略为：

- CSV 中给出可读降级值
- JSON 中保留 richer payload
- HTML/PNG 提供回看能力

---

## 7. Obsidian 中的推荐使用方式

### 7.1 想继续做结构化浏览

优先使用 `table.csv`：

- 可直接导入 Excel / WPS / Google Sheets
- 可通过 Obsidian 官方 CSV Importer 导入
- 可生成适合 Bases 使用的数据视图

### 7.2 想在 Obsidian 中直接以表格文件方式查看

继续保留 `table.csv` 即可。

如果需要增强体验，可选使用社区 CSV 编辑类插件，但不作为本项目主依赖。

### 7.3 想保留原貌

查看：

- `table.html`
- `table.png`

这两份文件是原貌兜底材料。

---

## 8. 导出报告中的记录方式

导出报告中新增数据表记录信息，统一记录：

- 来源知识库
- 来源文档
- 源语雀地址
- 对应 Markdown 路径
- 数据表标题
- sidecar 目录路径
- `csvPath`
- `rowsJsonPath`
- `schemaJsonPath`
- `htmlPath`
- `pngPath`
- `partial`
- `structuredSuccessRate`
- 是否保留快照兜底

这样可以用于：

- 后续批量审计
- 二次加工
- 查找哪些数据表提取不完整
- 后续继续增强数据表识别能力

---

## 9. 当前实现边界

当前版本已经实现：

- 检测语雀数据表类复杂块
- 优先做结构化导出
- 固定产出 CSV/JSON/HTML/PNG
- Markdown 中插入统一数据表区块
- 导出报告记录数据表信息
- 使用测试覆盖 CSV、sidecar 文件和 Markdown 区块回归

但仍然存在以下边界：

- 语雀数据表不是公开稳定格式，前端结构可能变化
- 某些复杂字段无法仅通过 DOM 无损还原
- richer cell payload 取决于页面中是否能读取到相应状态
- 复杂交互逻辑不会在 Obsidian 中原样重建

因此本方案的定位始终是：

> 以长期数据留存和后续可迁移性为核心，而不是复刻语雀数据表运行时体验。

---

## 10. 长期维护建议

后续如果继续增强该能力，建议沿以下顺序推进：

1. 优先提高列类型识别准确率
2. 增强 richer payload 提取能力
3. 为更多复杂字段提供更好的 CSV 降级文本
4. 增加真实语雀数据表样例回归测试
5. 在导出报告中增加“结构化提取不完整”的聚合统计

这能持续提高“可留存”和“可再利用”的质量，而不破坏当前稳定导出路径。

---

## 11. 最终原则

本项目关于语雀数据表的永久方案原则如下：

- 普通表格走 Markdown 表格
- 数据表走结构化 sidecar 导出
- CSV 负责通用交换
- JSON 负责完整留存
- HTML 负责可视化复核
- PNG 负责最终兜底
- Markdown 负责统一入口与可读性

这套策略的目标不是“复刻语雀”，而是“让数据得以长期留存并可持续迁移”。
